# AI Portfolio Assistant

A retrieval-augmented AI assistant that answers questions about my projects, technical skills, engineering experience, and current work using information grounded in my portfolio knowledge base.

The project combines **hybrid retrieval, query routing, Google Gemini, and FastAPI** to provide concise, portfolio-specific answers while reducing unsupported responses.

It is designed to power the conversational AI experience integrated into my AI Engineer portfolio website.

---

## Overview

A traditional portfolio requires visitors to manually browse project pages, skills, and experience sections.

The AI Portfolio Assistant provides a conversational interface instead. A recruiter, hiring manager, or technical visitor can ask questions such as:

- What AI projects has Timothy built?
- Has Timothy worked with RAG?
- What experience does Timothy have with Docker?
- What did Timothy contribute to the BundesHost project?
- What is Timothy currently working on?

Rather than relying only on the language model's general knowledge, the assistant retrieves relevant information from a dedicated portfolio knowledge base and uses that context to generate the response.

- Portfolio-specific Retrieval-Augmented Generation (RAG)
- Google Gemini embeddings and response generation

## Architecture

```text
Portfolio Visitor
       |
       v
Next.js Portfolio
       |
       | POST /chat
       v
FastAPI Backend
       |
       v
Query Router
       |
       +-------------------------------+
       |                               |
       | Focused Question              | Project Collection Question
       v                               v
Hybrid Retrieval                Project Overview Retrieval
       |                               |
       | Semantic Search               | One overview per project
       | + BM25                        |
       | + Query Expansion             |
       +---------------+---------------+
                       |
                       v
               Retrieved Context
                       |
                       v
                 Google Gemini
                       |
                       v
                Grounded Response
                       |
                       v
                Portfolio Visitor
```

The system uses two retrieval paths.

For focused questions, such as:

> Has Timothy used Docker?

the assistant performs hybrid semantic and lexical retrieval to identify the most relevant portfolio chunks.

For collection-style questions, such as:

> What AI projects has Timothy worked on?

the query router switches to project-overview retrieval so that the response receives coverage across the complete project portfolio rather than only the most semantically similar chunks.

## Retrieval Pipeline

### 1. Knowledge Base

Portfolio information is stored in:

```text
data/portfolio.md
```

The knowledge base contains structured information about:

- professional profile
- technical skills
- AI and machine-learning projects
- project contributions
- professional background
- current technical focus
- languages

### 2. Chunking

`src/chunking.py` converts the portfolio knowledge base into retrieval chunks.

Larger projects are separated into focused sections such as overview, contributions, infrastructure, and application details.

The current knowledge base produces **18 retrieval chunks**.

### 3. Semantic Retrieval

`src/embeddings.py` uses Google's embedding model to create vector representations of portfolio chunks and visitor questions.

The current embedding model is:

```text
gemini-embedding-001
```

Document chunks and user queries use their corresponding retrieval task types.

Document vectors are generated by explicit ingestion and persisted as a JSON
artifact. Importing retrieval or the API and starting the server never generate
document embeddings. Only actual focused queries request a query embedding.
SDK clients are constructed lazily on first use, so imports and successful
index-loading startup construct no provider clients. Application shutdown closes
clients that were used; explicit ingestion closes its embedding client too.

### Persistent index and ingestion

Generate the index explicitly in an authorized build/development environment:

```sh
.venv/bin/python -B -m src.ingest
```

**This command calls Gemini's embedding API and may incur charges.** It is
separate from the network-free runtime index loader and offline unit tests.
It is never run automatically on startup. Set `GOOGLE_API_KEY` and the existing
timeout settings first. No generation model requests are made during ingestion.

`RAG_INDEX_PATH` defaults to `data/index/portfolio.json`. Relative values resolve
from this repository's root, independent of the current working directory;
absolute paths can refer to a mounted artifact. Empty values are rejected.

The strict version-1 JSON format contains:

```text
schema_version: 1
embedding_model: gemini-embedding-001
embedding_dimensions: 3072
source_sha256: SHA-256 of the exact portfolio.md bytes
chunking_version: 1
chunks: [{id, heading, text, embedding}, ...]
```

Chunk IDs are SHA-256 hashes of the chunking-version prefix and complete chunk
text. Unchanged chunks have stable IDs. Document and query embeddings explicitly
request the same 3072 dimensions from the existing embedding model.

Ingestion captures the knowledge file once, applies the existing section and
project chunking rules, and generates document embeddings. It validates the
entire artifact before writing a temporary file in the target directory, flushes
and fsyncs that file, then atomically replaces the destination. Generation,
validation, write, or replacement failures leave the previous destination
intact; temporary files are cleaned up. The source is checked again before
publication to reject changes made while embeddings were generated. Atomic
replacement prevents partial JSON visibility; it is not a directory-fsync
guarantee against every power-loss scenario. Avoid concurrent ingestion jobs.

Startup validates exact top-level/chunk fields, schema/chunking versions, model,
dimensions, source hash, chunk count/order/IDs, headings and text, duplicate IDs,
nonempty chunk bodies, and finite numeric nonzero vectors. Booleans and numeric
strings are not vector numbers. Duplicate JSON keys, NaN/Infinity, and files
larger than 16 MiB are rejected. JSON is data only: no pickle or executable
deserialization is used. Hashes establish freshness and content consistency;
they do not authenticate the producer or prove embedding quality.

The FastAPI lifespan loads and validates the artifact once, builds the BM25
index locally, and stores a retrieval snapshot on the app. Both focused and
collection answers use that snapshot. Changing knowledge or replacing the
artifact does not hot-reload a running worker. After editing knowledge, regenerate
the index and restart/deploy the matching pair. Any source byte change, including
whitespace, invalidates an old artifact at the next startup. Bump
`CHUNKING_VERSION` when chunking/ID semantics change and `SCHEMA_VERSION` when
the serialized format changes, then regenerate.

Deploy the reviewed `data/portfolio.md` and its generated artifact together in
the image/release, or mount the artifact at `RAG_INDEX_PATH`. The runtime only
needs read access to the index; temporary-file permissions default to owner
read/write, so grant the runtime service user read access during packaging.
Generate in a controlled build job, transfer the complete artifact securely, and
start the server only after both files are present. Every worker loads the same
artifact without embedding charges. Runtime credentials are still needed for
query embeddings and generation. Do not generate in every replica's startup.

The default `data/index/` directory is **Git-ignored**. This keeps generated
vectors and copied portfolio text out of source history and avoids committing
unreviewed knowledge. The tradeoff is that cloning the repository does not
provide a runnable retrieval artifact: it must be generated or supplied by the
deployment process. Custom paths outside `data/index/` need their own ignore
rule or must remain outside the repository. Do not force-add generated artifacts
without an explicit content review and approval.

Missing, corrupt, incompatible, or stale artifacts fail startup with a generic
message; the server never silently regenerates them. Operator logs include a
safe diagnostic code such as `missing_index`, `stale_source`, `embedding_model`,
`embedding_dimensions`, `vector_dimensions`, `chunk_mismatch`, or
`invalid_json_or_unreadable_index`. For missing indexes, verify the configured
path and artifact packaging/read permissions. For stale/chunk-mismatch errors,
verify that the source, chunking code, and artifact belong to the same release;
regenerate in the authorized ingestion environment. For malformed/model/dimension
errors, replace the artifact with a validated one instead of editing vectors by
hand. Ingestion failures print no provider exception text or secrets.

### 4. BM25 Lexical Retrieval

Semantic similarity is combined with BM25 lexical retrieval.

This helps the system retrieve information containing important technical terms such as:

- MLflow
- Docker
- RAG
- FastAPI
- project names

The hybrid retrieval score currently combines:

```text
85% semantic similarity
15% normalized lexical relevance
```

### 5. Query Expansion

`src/query_expansion.py` provides deterministic expansion for selected technical terms and phrases.

Examples include mappings between:

```text
RAG -> retrieval-augmented generation
experiment tracking -> MLflow / model tracking
independently -> solo project / individual project
```

This improves retrieval without requiring an additional language-model request.

### 6. Query Routing

Not every question should use the same retrieval strategy.

`src/query_router.py` identifies broad questions asking about the project portfolio as a collection.

Focused questions use:

```text
Hybrid semantic + BM25 retrieval
        |
        v
Top 3 relevant chunks
```

Broad project questions use:

```text
Project collection route
        |
        v
One representative overview per project
```

This prevents broad questions from returning only the projects that happen to have the highest semantic similarity.

## Grounded Generation

After retrieval, the selected portfolio context is provided to Google Gemini.

The generation prompt instructs the model to:

- answer using only retrieved portfolio information
- avoid inventing projects, skills, employers, qualifications, or results
- distinguish completed projects from projects still in development
- state when requested information is unavailable
- keep answers concise and useful for recruiters and technical visitors

This makes retrieval the source of portfolio facts while the language model handles natural-language response generation.

## API

The assistant is exposed through a FastAPI backend.

### Health Check

```http
GET /health
```

Example response:

```json
{
  "status": "ok",
  "service": "AI Portfolio Assistant"
}
```

### Chat

```http
POST /chat
```

Example request:

```json
{
  "message": "Has Timothy used Docker?"
}
```

Example response structure:

```json
{
  "answer": "..."
}
```

Messages are validated before processing and are limited to 1,000 characters.
The only accepted JSON field is `message`. Successful responses remain
`{"answer": "..."}`.

### Readiness

`GET /ready` returns HTTP 200 with `{"status":"ready"}` only while a validated
index is loaded. Before lifespan startup or after shutdown, it returns 503 with
`{"status":"not_ready"}` if the app is served without a completed lifespan.
`GET /health` retains its original response. Neither endpoint contacts Gemini
or reveals paths, credentials, or configuration details. Readiness does not
check live provider availability or quota. A normal server with a missing or
invalid artifact fails startup altogether, so it will not serve either endpoint;
deployment readiness probes must also treat an unreachable server as unready.

### Reliability and cost controls

Settings are read at startup. `GEMINI_NETWORK_POLICY` accepts `auto` or `ipv4`.
`CHAT_DEADLINE_SECONDS` accepts finite numeric
seconds between 0.01 and 120 inclusive; its default is 40. Fractional values
support short offline tests. Other numeric settings below are positive integers.
Invalid values fail startup without echoing the supplied value. Restart after changing settings.
The generation and embedding models and hybrid retrieval ranking are unchanged.

| Environment variable | Default | Meaning |
| --- | ---: | --- |
| `GEMINI_NETWORK_POLICY` | auto | SDK networking, or opt-in IPv4 source binding for synchronous Gemini requests |
| `CHAT_DEADLINE_SECONDS` | 40 | Overall chat-processing deadline in seconds, monotonic |
| `GEMINI_EMBEDDING_TIMEOUT_MS` | 10000 | Embedding HTTP request timeout in milliseconds |
| `GEMINI_GENERATION_TIMEOUT_MS` | 20000 | Generation HTTP request timeout in milliseconds |
| `GEMINI_MAX_OUTPUT_TOKENS` | 1024 | Combined thinking and visible output ceiling; integer from 1 to 65536 |
| `GEMINI_THINKING_LEVEL` | LOW | Thinking level for `gemini-3.8-flash`: LOW, MEDIUM, or HIGH |
| `CHAT_MAX_BODY_BYTES` | 8192 | Maximum chat request body, measured in bytes |
| `CHAT_MAX_CONCURRENT` | 4 | Admitted chat requests per worker process |
| `CHAT_RATE_LIMIT_REQUESTS` | 20 | Requests per peer address per fixed window |
| `CHAT_RATE_LIMIT_WINDOW_SECONDS` | 60 | Fixed-window duration in seconds |
| `CHAT_RATE_LIMIT_MAX_CLIENTS` | 1024 | Maximum live rate-limit entries per process |

Both Gemini clients explicitly use one total attempt (zero automatic retries).
This was checked against the installed `google-genai` 2.30.1 SDK: `HttpOptions`
uses milliseconds, and `HttpRetryOptions.attempts` includes the initial request.
Embedding timeouts cover explicit ingestion as well as question embeddings.

### Generation completion and token budgets

The initial evaluation settings are `GEMINI_MAX_OUTPUT_TOKENS=1024` and
`GEMINI_THINKING_LEVEL=LOW`; these are starting points, not measured optimal
values. The token ceiling includes thinking as well as visible answer tokens,
so even a concise answer can be truncated when the combined ceiling is too low.
The existing concise, portfolio-grounded answer instructions remain in place.
An existing `.env` or process environment overrides these defaults; review any
older `GEMINI_MAX_OUTPUT_TOKENS=512` setting before a controlled live test.

The installed `google-genai` 2.30.1 supports
`GenerateContentConfig.thinking_config.thinking_level`. The unchanged
`gemini-3.8-flash` model supports LOW, MEDIUM, and HIGH. MINIMAL and disabling
thinking are not offered by this application; incompatible or invalid settings
fail configuration validation instead of silently falling back. See the
[model guide](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/guides/gemini-3-8-flash)
and [thinking token limits](https://aistudio.google.com/docs/thinking#token-limits).

Only nonempty visible text with explicit `STOP` completion is returned as
`{"answer": "..."}`. `MAX_TOKENS` and `CONTINUATION` are incomplete responses;
safety blocks, missing candidates/reasons, malformed reasons, and all other
finish reasons are also rejected with the existing sanitized HTTP 502 body.
The application does not retry generation or request continuation. The
generation config explicitly sets the SDK's public
`automatic_continuation=False` option: a provider `CONTINUATION` response with
a continuation token is returned to application validation and rejected, rather
than followed by another generation HTTP request. This is independent of
`HttpRetryOptions(attempts=1)`, which separately disables HTTP retries. Offline
tests exercise both policies using the actual SDK with an in-memory transport.
The 20-second generation transport timeout, 40-second overall deadline, one SDK
attempt, and concurrency lifecycle are unchanged.

When a response is available before the deadline, the existing request log
includes a `generation` object with an allowlisted `finish_reason` category and
optional `prompt_token_count`, `candidates_token_count`, `thoughts_token_count`,
and `total_token_count`. Missing or malformed counts become null rather than
zero. Unknown reason strings become `UNKNOWN`; malformed and missing reasons
use fixed categories. No raw metadata, free-form finish messages, response or
thought text, prompts, context, or credentials are logged or exposed publicly.
Workers completing after a deadline cannot emit a later success log or add
generation metadata to that completed request.

`STOP` confirms provider completion, not factual correctness or grammatical
completeness. Grounding still depends on retrieved knowledge and the prompt.
These settings require controlled live evaluation; they cannot guarantee that
every answer fits the budget or arrives before the deadline.

### Gemini network policy

The default `GEMINI_NETWORK_POLICY=auto` leaves the SDK's transport selection,
IPv4/IPv6 behavior, environment/system proxy handling, and TLS configuration
unchanged. No startup connectivity probes or automatic family switching occur.

On a direct network where IPv6 is unusable but IPv4 works, explicitly select:

```env
GEMINI_NETWORK_POLICY=ipv4
```

Apply the setting to the affected deployment/process and restart it through
your normal deployment procedure. It is not automatically written to `.env`
or enabled on every environment. Changing the policy does not require ingestion
or a new persistent index. A temporary verification server can receive the
setting through its environment without changing or restarting another server.

All three paths use the same provider options factory: query embeddings,
explicit document ingestion, and answer generation. The IPv4 option uses the
SDK's public `types.HttpOptions(client_args={"transport": ...})` passthrough and
HTTPX's public `HTTPTransport(local_address="0.0.0.0", verify=True, retries=0)`.
The local wildcard is an IPv4 source bind, **not a Google destination IP**.
The OS rejects incompatible IPv6 source/destination combinations before their
connect attempts; IPv4 destinations are still obtained through normal DNS.
The official SDK hostname remains intact for HTTP routing, TLS hostname
verification, and SNI. Certificate validation stays enabled, with HTTPX's normal
CA configuration including `SSL_CERT_FILE`/`SSL_CERT_DIR`. There is no global
socket patch, DNS change, provider IP list, or effect on unrelated HTTP clients.

The existing embedding/generation timeouts, one SDK attempt, and 40-second
application deadline remain in force. The SDK owns the HTTPX clients that
receive these transports, so existing SDK client shutdown closes the active
synchronous transports; externally owned HTTPX clients are not injected.

Shutdown attempts generation-client and embedding-client cleanup independently.
If either close fails, the other is still attempted and client references are
cleared. A fixed structured log names only the failed clients, and shutdown
raises a generic error without forwarding provider exception messages or chains.
Failures are reported rather than silently ignored; a failed close cannot
guarantee resource release. Synchronous client close/lock waits can still block,
so process supervision and an external shutdown limit remain necessary.

An explicit HTTPX transport disables automatic proxy discovery. Consequently,
`ipv4` fails configuration/client setup if an HTTP, HTTPS, or ALL proxy is
configured through the environment or operating system, rather than silently
bypassing a required proxy. This conservative check also rejects proxy settings
that might exclude Gemini through NO_PROXY. Use `auto` on proxy-managed networks
until an explicit proxy-compatible transport policy is reviewed.

This integration is verified with the locked `google-genai` 2.30.1 and HTTPX
0.28.1 versions. The policy covers the application's synchronous SDK calls;
moving to async SDK requests or mutual-TLS client certificates requires a
corresponding transport review. It cannot repair DNS outages, IPv4 firewall
blocks, service errors, or credential/quota problems. Review the integration
when upgrading the SDK/HTTPX rather than relying on private internals.

Public references:
[SDK HTTP options](https://googleapis.github.io/python-genai/genai.html#genai.types.HttpOptions)
and [HTTPX transports](https://www.python-httpx.org/advanced/transports/).

Recommended credential-free IPv4 connectivity check, on a direct network with
no proxy configured (a 404 response still confirms working HTTPS):

```sh
curl -q --ipv4 --connect-timeout 3 --max-time 10 \
  --silent --show-error --output /dev/null \
  --write-out 'HTTP %{http_code}; TCP %{time_connect}s; TLS %{time_appconnect}s; total %{time_total}s\n' \
  https://generativelanguage.googleapis.com/
```

`-q` disables curl's user configuration. Do not add API keys, authorization,
or model endpoint paths. This checks connectivity, not model permissions. The
offline transport suite additionally verifies the actual SDK options, source
binding, TLS verification flags/SNI, serialization, and owned-client shutdown
without external network access.

### Deadline behavior

**Provider timeouts and the overall application deadline are separate.** The SDK
passes the timeout to its HTTP transport and supplies a server timeout hint.
Transport phase/inactivity timeouts do not promise a strict wall-clock deadline.
A focused question performs embedding followed by generation, plus local work.
The existing embedding/generation transport limits remain 10/20 seconds by
default, with one attempt. The application adds a monotonic 40-second deadline
covering body admission, validation/worker-pool waiting, routing, lazy client
initialization and lock waits, query embedding, hybrid retrieval, generation,
and response preparation. `/health` and `/ready` are outside this deadline;
their lightweight async handlers do not wait for the provider worker pool.

The synchronous endpoint still runs in Starlette/AnyIO's worker pool. A bounded
ASGI supervisor waits for the operation using `asyncio.wait`, rather than waiting
for cancellation of a blocked thread. It buffers the JSON response until the
operation completes. On expiry it sends the existing sanitized HTTP 504 body
immediately, requests cancellation of the ASGI operation without awaiting it,
and discards any late headers/body. No extra executor or unbounded work queue is
created: every supervised operation first reserves a chat capacity lease.

**HTTP 504 does not guarantee cancellation of a running Gemini request.** A
synchronous call may continue and incur provider charges. Its lease is retained
until both the worker and its ASGI operation have finished, then released exactly
once. Work cancelled before worker admission cannot later start provider calls.
Deadline checks between phases prevent a late embedding result from triggering
generation. While all slots are held by outstanding workers, new chats return
503. Even an ASGI operation that suppresses cancellation keeps its slot until
it exits, so abandoned operations cannot accumulate without bound.

The deadline requires a responsive event loop; it cannot preempt synchronous
event-loop blocking, force-kill Python threads, or guarantee network delivery to
a stalled client. It is not a hard real-time guarantee. Configure ingress
header/connection/upload/request limits too, and supervise worker processes so
permanently stuck provider work can be recovered operationally. This phase does
not restart or manage any running server process.

Admission uses a non-blocking bounded semaphore; saturated requests are rejected
immediately rather than queued. Rate limiting uses connection peer addresses,
monotonic fixed windows, and bounded memory. Attempts count even if later
rejected by validation or concurrency limits. Expired entries are removed;
when the client table is full, new peers receive 503 instead of evicting live
entries and bypassing the limit. Fixed windows permit bursts around a reset.
Body bytes are counted from ASGI receive frames before JSON parsing, including
requests without Content-Length or with a misleading smaller value. Declared
oversized bodies are rejected early. Admission covers upload/parsing too, so
slow uploads occupy slots until the application deadline; ingress limits are
still needed before requests reach the application.

The app never reads `X-Forwarded-For`, `Forwarded`, or similar headers to choose
a rate-limit identity. It uses the ASGI connection peer. Run Uvicorn with
`--no-proxy-headers` unless you have explicitly established trusted proxies;
otherwise the server itself may rewrite the peer before the app receives it.
Behind an untrusted/unconfigured proxy, users share its peer bucket. To enable
forwarding later, trust only known proxy addresses at the server and require
that proxy to replace visitor-supplied forwarding headers. Do not trust `*`.

Concurrency and rate limits are **process-local**, reset on restart, and multiply
with worker/instance count. They are not a global spending cap or distributed
abuse defense. Set provider quotas/billing controls and deployment-wide ingress
limits before exposing the service publicly; distributed peers can each use
their own bucket. No Redis, database, authentication service, or dependency was
added for these controls.

| HTTP status | Meaning |
| --- | --- |
| 400 | Invalid or duplicate Content-Length |
| 413 | Request body exceeds the byte limit |
| 422 | Invalid JSON, message, or unexpected JSON fields |
| 429 | Local peer rate limit reached; `Retry-After` gives remaining window seconds |
| 503 | Chat capacity/client table exhausted, or provider quota reached |
| 504 | Overall chat deadline expired, or embedding/generation transport timed out |
| 502 | Empty, incomplete, blocked, or invalid model output; provider transport failure; SDK API error |
| 500 | Unexpected internal failure |

Provider failures retain the safe body
`{"detail": "The AI assistant could not generate a response."}`.
Local protective rejections also use a `detail` string. Capacity rejections
suggest retrying after one second, a full client table reports its earliest
expiry, and provider quota failures conservatively suggest 60 seconds. These
values are hints; clients should back off and avoid indefinite automatic retries.

Operational JSON logs go to stderr via the `portfolio.api` logger. Each entry
contains a generated request ID, HTTP status, duration in milliseconds, and a
provider failure category when applicable. Chat entries also include
`phase_timings_ms` and `active_phase`. Timing names are fixed:
`request_admission`, `worker_admission`, `query_routing`,
`embedding_client_initialization`, `embedding`, `hybrid_retrieval`,
`generation_client_initialization`, `generation`, and `response_preparation`.
Request admission includes bounded body reading; worker admission includes
validation and waiting for the shared AnyIO worker pool. Nested phase timings
are exclusive: embedding/client setup time is subtracted from hybrid retrieval,
and client initialization is subtracted from its embedding/generation phase.
Total request duration also covers response serialization and response sending.
On expiry, logs capture elapsed phase times and the active phase at response time,
with category `deadline`; SDK transport timeouts retain category `timeout`.
Each HTTP request emits one completion entry. Late worker completion does not
emit a success record for a request that already returned 504.
It does not log visitor messages,
portfolio context, prompts, exception text, keys, or authorization headers.
`X-Request-ID` is generated by the app rather than trusted from the visitor;
it and `Retry-After` are exposed to permitted CORS origins. Disconnects before
the handler starts and cancelled requests are logged as 499. Deployments
should retain these minimal logs and avoid enabling SDK HTTP debug logging.

The offline regression suite exercises body streaming, rate resets, concurrent
admission, provider policies, safe errors, and logging without contacting Gemini:

```sh
.venv/bin/python -B -m unittest discover -s tests -v
```

Compared with Phase 2A, tests now require 422 for extra fields, 504 for provider
timeouts, and 502 for empty/blocked responses. These assertions enforce the new
error policy; successful response schemas and existing test scenarios remain.

## Protected staging API

Local development remains unauthenticated by default. For protected staging,
explicitly set `STAGING_AUTH_ENABLED=true` and supply `STAGING_AUTH_TOKEN`
through the deployment platform's runtime secret mechanism. The token must be
43–256 ASCII URL-safe characters (`A-Z`, `a-z`, digits, `_`, `-`). Generate at
least 32 random bytes using Python's `secrets.token_urlsafe(32)` in a trusted
environment and store the result securely. Format validation cannot establish
randomness. An enabled staging configuration with a missing/invalid token fails
before the application starts. The real local `.env` is not needed in the image.

All HTTP routes except `GET`/`HEAD` on `/health` and `/ready` require exactly one
`Authorization: Bearer <token>` header in staging. This default-deny middleware
also protects `/chat/` and future HTTP endpoints. Missing, malformed, duplicate,
or incorrect credentials return `401` with `{"detail":"Unauthorized."}` before
provider admission, body processing, or client initialization. Token comparison
uses `secrets.compare_digest`. Query/body credentials and cookies are not used.
CORS preflight requests can complete without authentication but cannot invoke
provider operations. Documentation routes `/docs`, `/redoc`, and `/openapi.json`
are not registered in staging; local development retains them. Unauthenticated
requests to non-health paths, including disabled documentation paths, return 401;
authenticated requests to disabled paths return 404.

Use a trusted CLI/API client over HTTPS initially. Never put a staging token in
`NEXT_PUBLIC_*`, browser JavaScript, URLs, request bodies, source control, logs,
Docker build arguments, or shared request collections. Avoid shell history and
command-line exposure when supplying it. A browser integration requires a
trusted server-side component that authenticates tester sessions, checks CSRF
and origin requirements, applies limits, and adds the backend token server-side.
An unauthenticated forwarding endpoint would expose paid calls again. A shared
token has no individual attribution: restrict distribution and rotate it on
leakage or tester offboarding. New token values require a process restart.

Set `FRONTEND_ORIGINS` to an empty value for CLI-only staging, or an explicit
comma-separated HTTP(S) origin allowlist. When omitted in staging it defaults
to empty. Wildcards, credentials, paths, queries, fragments, and malformed ports
are rejected. The local origins in `.env.example` must be explicitly replaced
or cleared for staging. Staging CORS allows only GET/POST, Authorization and
Content-Type headers, and does not enable credentialed cookies. CORS is browser
policy, not authentication: a valid token holder can use a non-browser client.

| Setting | Default | Meaning |
| --- | --- | --- |
| `STAGING_AUTH_ENABLED` | `false` | Explicit `true`/`false`; protected mode is opt-in |
| `STAGING_AUTH_TOKEN` | empty | Required runtime secret when protected mode is enabled |
| `STAGING_BUDGET_REQUESTS` | `10` | Positive aggregate authenticated attempts per window |
| `STAGING_BUDGET_WINDOW_SECONDS` | `60` | Positive fixed-window duration in monotonic seconds |

The aggregate budget is active only in protected mode and independent of peer
IP or forwarding headers. It has one fixed identity and bounded memory. Exhaustion
returns 429 with a rounded-up `Retry-After`. Authentication failures and health
checks do not consume it. Other authenticated HTTP attempts count conservatively,
including invalid requests, unknown routes, redirects and provider failures;
following `/chat/` to `/chat` consumes two attempts, so prefer `/chat` directly.
Existing peer rate limits, body limits, non-blocking concurrency leases and the
40-second chat deadline remain in effect. A 504 does not cancel an already-running
Gemini request; its concurrency slot remains held until the worker actually exits.
Future endpoints inherit authentication/budget protection, but must separately
use appropriate body, concurrency and deadline protections if they perform paid work.

This budget is process-local, resets on restart, permits fixed-window boundary
bursts, and multiplies across workers, instances or overlapping deployments. It
is not a hard monetary spending cap. Start with one instance/worker and retain
provider quotas, staging spend controls, billing alerts and operator access
restrictions. Keep `--no-proxy-headers` until proxy trust is explicitly reviewed;
Render callers may otherwise share a peer bucket. Runtime isolation and the
residual CVE dispositions remain separate deployment requirements.

Validation errors now use allowlisted generic messages/locations and omit input,
context, and attacker-controlled field names in both local and protected modes.
Operational logs retain status/request IDs and sanitized timing metadata; they
never include Authorization headers, tokens, visitor messages, or provider text.

Verify staging with offline tests first. Health/readiness checks require no token
and never call Gemini. A valid `/chat` request can incur provider charges and
requires separate live-test authorization. No images or resources are published
by enabling these settings in local tests.

## Production Docker package

The multi-stage Dockerfile pins Python `3.11.18-slim-bookworm` and uv `0.10.2`
by immutable multi-platform registry digests. The dependency stage uses the
committed `uv.lock` with `uv sync --frozen --no-dev --no-install-project
--no-editable --no-build`; only locked runtime dependencies are installed,
without source builds or managed Python downloads. uv and its cache remain in
the builder, not the runtime image. BuildKit and registry/package access are
needed for a first build. No host dependency installation is required.

The final image contains `/app/.venv`, thirteen runtime Python modules,
`pyproject.toml`, `uv.lock`, `release.sha256`, `data/portfolio.md`, and the
validated `data/index/portfolio.json`. Ingestion, evaluators, tests, local
configuration, and credentials are not packaged. It runs as UID/GID `10001`,
with one Uvicorn worker, no reload, host `0.0.0.0`, and `${PORT:-8080}`.
An exec startup command forwards termination signals to Uvicorn. The image's
health check calls `/ready` using the standard library without contacting Gemini.

### Prepare the existing index as a release artifact

Docker does not obtain Git-ignored files from GitHub. Before preparing a release,
supply the existing reviewed index at `data/index/portfolio.json`, together with
the matching knowledge source. For this release it contains 18 validated chunks.
Do not force-add the artifact to Git or regenerate it during builds/startup.

From the repository root, prepare a new context outside the checkout:

```sh
release_parent="$(mktemp -d)"
release_context="$release_parent/context"
.venv/bin/python -B scripts/prepare_docker_context.py "$release_context"
docker build --tag ai-portfolio-assistant:phase4b "$release_context"
```

The helper validates the existing index without importing Gemini clients,
snapshots only explicitly named files, rejects symlinked inputs and existing
destinations, and writes deterministic SHA-256 checksums for runtime inputs.
It never copies the whole data directory. Source and index bytes are preserved.
The Dockerfile verifies those checksums and runs the existing index validator
in a build step with networking disabled. Missing, corrupt, stale, or mismatched
artifacts fail preparation/build, and startup retains its own validation.

Use the helper-generated context, not `docker build .`: the checksum manifest
is generated only in that context. `.dockerignore` additionally denies every
file except the exact build/runtime allowlist, independently of `.gitignore`.
This excludes `.env*` (including `.env.example`), `.codex`, Git history, virtual
environments, credentials, tests, caches, logs, and temporary files. Review any
future additions to both the context allowlist and Dockerfile. Transfer release
artifacts through controlled CI/private artifact storage; checksums establish
consistency, not authenticity. Build/deployment access must be restricted.

The root-owned packaged source/index files have mode `0444`; their parent
directories are not writable by the application user. No runtime ingestion or
writable persistent disk is required. Release a matching knowledge/index pair
and retain the previous release for rollback. Do not bind-mount a writable
replacement over the packaged index in production.

### Run locally or supply deployment configuration

Supply `GOOGLE_API_KEY` at runtime through the platform's secret mechanism.
For the following command, securely export it in the invoking shell first;
`--env GOOGLE_API_KEY` passes it without placing its value in the command text.
Do not use Docker build arguments, image ENV declarations, or source files for
credentials. Users with Docker daemon access can inspect runtime environment
values, so restrict that access too.

```sh
local_container="$(docker run --detach --read-only \
  --cap-drop ALL --security-opt no-new-privileges:true \
  --tmpfs /tmp:rw,noexec,nosuid,size=16m \
  --publish 127.0.0.1::8080 \
  --env GOOGLE_API_KEY \
  --env FRONTEND_ORIGINS=http://localhost:3000 \
  ai-portfolio-assistant:phase4b)"
docker port "$local_container" 8080/tcp
```

The ephemeral host port avoids port 8000 and existing containers. After startup,
use the address printed by `docker port` with `curl --fail --max-time 5` for
`/health` and `/ready`; expected results are HTTP 200 with the existing health
body and `{"status":"ready"}` respectively. Only these endpoints are needed
for packaging checks. `/chat` makes live provider calls and requires separate
authorization. Stop/remove only this container when finished:

```sh
docker stop --time 10 "$local_container"
docker rm "$local_container"
```

`PORT` defaults to 8080; set it to the platform's supplied value and match the
container target port when publishing locally. `RAG_INDEX_PATH` defaults in the
image to `/app/data/index/portfolio.json`; relative overrides still resolve
against `/app`. Set `FRONTEND_ORIGINS` to the exact HTTPS production frontend
origin(s). All token/thinking, Gemini transport, deadline, body-size, rate, and
concurrency settings retain the defaults in the configuration table above.
Networking defaults to `auto`; choose `ipv4` only for an affected direct network.
No real `.env` is copied, changed, or required inside the image.

### Guaranteed offline container smoke test

Once a Docker daemon is available, the following uses a fake key and disables
all container networking. It invokes no chat requests, cannot reach Gemini,
and leaves existing containers and port 8000 alone:

```sh
smoke_container="$(docker run --detach --network none --read-only \
  --cap-drop ALL --security-opt no-new-privileges:true \
  --tmpfs /tmp:rw,noexec,nosuid,size=16m \
  --env GOOGLE_API_KEY=offline-container-test-key \
  ai-portfolio-assistant:phase4b)"
```

Run health/readiness checks inside that isolated container (startup is allowed
up to 20 seconds), verify its user and artifact, then remove only that container:

```sh
docker exec -i "$smoke_container" python -B - <<'PY'
import http.client
import json
import os
from pathlib import Path
import time
from src.index_store import load_index

assert os.getuid() == 10001
index_path = Path(os.environ['RAG_INDEX_PATH'])
index = load_index(index_path)
assert not os.access(index_path, os.W_OK)
assert not os.access(index_path.parent, os.W_OK)
for excluded in ('.env', '.git', '.codex', 'tests', 'scripts', 'src/ingest.py'):
    assert not Path('/app', excluded).exists()
assert not Path('/usr/local/bin/uv').exists()
for endpoint in ('/health', '/ready'):
    deadline = time.monotonic() + 20
    while True:
        connection = http.client.HTTPConnection('127.0.0.1', int(os.environ['PORT']), timeout=2)
        try:
            connection.request('GET', endpoint)
            response = connection.getresponse()
            body = json.loads(response.read())
            assert response.status == 200
            if endpoint == '/ready':
                assert body == {'status': 'ready'}
            print(endpoint, response.status, body)
            break
        except OSError:
            if time.monotonic() >= deadline:
                raise
            time.sleep(0.2)
        finally:
            connection.close()
print('Validated non-root, read-only container index:', len(index.chunks), 'chunks')
PY
docker stop --time 10 "$smoke_container"
docker rm "$smoke_container"
```

The host offline suite also covers release allowlisting, symlink rejection,
matching source/index bytes, checksums, and failure cleanup:

```sh
.venv/bin/python -B -m unittest discover -s tests -v
git diff --check
```

Actual image/container checks require a running Docker daemon. A Docker CLI
without its daemon cannot build or run this package; start Docker separately
and rerun the commands above. Do not infer image success from unit tests alone.
The initial package still needs an image vulnerability scan, deployment-region
connectivity/proxy checks, ingress limits, provider quotas/cost controls, and
staging measurements. Limits remain process-local; blocked synchronous workers
and shutdown can require external process recovery. Update pinned image digests
deliberately for security releases. Reproducibility means pinned build inputs
and dependencies, not a promise of identical image bytes across architectures.
